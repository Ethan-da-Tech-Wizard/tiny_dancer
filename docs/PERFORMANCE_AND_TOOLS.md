## The model and this machine

GPT-OSS-20B is a mixture-of-experts transformer: approximately 20.9 billion total parameters, 3.6 billion active per token, 24 layers, 32 experts per layer and four selected experts per token. These are architecture facts from the [OpenAI model introduction](https://openai.com/index/introducing-gpt-oss/) and [model documentation](https://developers.openai.com/api/docs/models/gpt-oss-20b). Selecting four experts reduces computation; it does not remove the need to store every expert. The converted Picchio weights are retained on the USB GameDrive, with bounded RAM and GPU caches. This upgrade changes neither those weights nor their precision.

## Changes implemented and measured

Source inspection confirms that `run_prefill_range` groups positions by selected expert and calls CPU `expert_apply` for those positions. `pgpu_moe_layer` currently accepts a single token. Moving that path to CUDA efficiently needs a new grouped, multi-position API/kernel with bounded buffers and cache residency; repeatedly calling the single-token API risks extra transfers and launches. NVIDIA's [CUDA best practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html) and [advanced host programming guide](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-host-programming.html) support minimizing transfers and batching small operations. The proposed prefill design is an inference from those sources and this engine's code, not a demonstrated improvement.

The existing CUDA numeric self-test still passes: INT8 output-head CPU/GPU top token matches, maximum absolute difference **3.815e-6**; INT4 gs64 expert difference **1.431e-6**. Its output-head timing, GPU 4.85 ms versus single-thread CPU 271.8 ms, is only a matrix microbenchmark. It does not measure complete prompt processing or task speed. [GPU investigation evidence](gpu-prefill-investigation.json) and `logs/gpu-investigation-numeric-test.log` preserve the run. No new kernel, approximation, buffer budget or production cache setting was enabled.

The pinned source is `a86393b90bd8ccc1935139a14d619cf409f6ca89`, MIT licensed. The active local patch is [picchio-local.patch](picchio-local.patch). No new native kernel or approximate arithmetic was enabled during this upgrade.

1. **Exact prefill prefetch.** The native `run_prefill_range` already knows the entire next expert block and can preload it while the current block computes. Existing `PREFETCH` also enables a decode-time prediction path, which can add unwanted reads. A promising experiment is separating an exact prefill-only setting from decode prediction. Keep the same cache budget, routing, arithmetic and model. Compare identical prompts and generated token IDs, disk reads, CPU time and peak memory; use repeated alternating runs because Linux page-cache warmth can dominate a USB-drive comparison.
2. **GPU batched prefill.** The current prefill loop calls CPU `expert_apply` for every selected position, even though single-token decoding supports GPU experts. Group positions by expert, upload each expert once, and evaluate several positions on the GPU together. Retain all four selected experts and original activation precision. This requires an actual CUDA implementation, numeric checks of layer outputs/logits, and task evaluations. A kernel improvement has not been demonstrated yet.
3. **Cache reuse for active tasks.** Keep stable prompt prefixes and avoid re-reading a whole page when a smaller section suffices. Measure actual GPU residency and disk bytes before altering cache policy. Increasing a cache consumes more memory, so it is not automatically a fit for the owner's resource goal.
4. **Exact speculative verification.** Picchio already includes draft/verification and prompt-lookup probes. It is only useful if exact target verification accepts enough proposed tokens to outweigh extra compute and memory. A smaller model is not a replacement for the final target. No additional draft model has been downloaded.

`IDOT` quantizes activations and is explicitly approximate upstream. Reducing the selected experts or silently substituting another model also changes the result. These are outside the current optimization approach. No universal speed multiplier or accuracy guarantee is implied by this investigation.

## MCP and open source tooling

MCP is a tool protocol. It can connect this local model to local software; it does not require Claude or Gemini inference. Gemini CLI's source is [Apache-2.0](https://github.com/google-gemini/gemini-cli/blob/main/LICENSE), but its normal setup uses Google's model service. Claude Code's `mcp serve` exposes tools, but neither CLI was installed for this project.

The intended extension is a local MCP client with tool discovery on demand, bounded output, existing audit/checkpoint/cancellation handling, and explicit per-server configuration. A large permanent tool catalog would increase prefill cost. Prefer a server that adds a useful missing capability, such as structured Git operations or editor language-server diagnostics, rather than duplicating the current terminal/files/browser tools. The [official reference servers](https://github.com/modelcontextprotocol/servers) and [Playwright MCP](https://github.com/microsoft/playwright-mcp) are research candidates, not installed components. Review the specific server's source and terms before adopting it; no server inherits the project's Apache license automatically.

For every actual dependency addition: pin source/package versions, retain full license and bundled notices, refresh `requirements.lock.txt` if applicable, run `scripts/collect_licenses.py` then `--check`, and record implementation and validation in `STATE.json` and `SESSION_LOG.md`. Current inventory contains 241 texts, 45 Python distributions and 28 direct host dependencies. The existing Rust compiler, Cargo and rustup are now included with their full notices; no compiler or crate was installed for this qualification.
